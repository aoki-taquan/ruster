# FEとCEの分け方

状態: 叩き台（2026-11-06）。メッセージの具体的な形式はまだ決めていない。

この文書は[`../charter.md`](../charter.md)の「構成の基本」を具体化する。

## 用語

- FE（forwarding element、転送部）: パケットを受け取り、表を引いて送り出すプロセス。rusterの本体。
- CE（control element、制御部）: FEの表を書き換えたり、FEからパケットを受け取ったりする別プロセス。
- 表: FEが転送に使うデータ。経路、近隣、インターフェースとアドレス、NATルール、firewallルールなど。

## FEとCEの線引き

パケットの到着ペースで作られる状態はFEに置く。それ以外の状態と、相手と会話するプロトコルはCEに置く。

| 処理 | 置き場所 | 理由 |
|---|---|---|
| 転送、TTL、checksum、MAC書き換え | FE | パケットごとの処理 |
| NATセッション、firewallの状態追跡 | FE | フローごとに作られ、外に問い合わせると間に合わない |
| フラグメント処理、ICMPエラー生成（流量制限付き） | FE | パケットごとの処理 |
| トンネルのカプセル化（MAP-E、DS-Lite） | FE | トンネル内の通信はすべて転送 |
| ルータ宛て通信の分類と流量制限 | FE | 攻撃を受けても制御通信を守るため |
| ARP/ND（問い合わせ、再送、GARP、DAD、衝突検出） | CE | 近隣の数の分しか状態がなく、プロトコルの状態遷移を持つ |
| 経路計算（RIB）、静的経路の選択 | CE | 相手と会話するプロトコル、ポリシー |
| DHCP、DNS、RA、PPPoEの制御 | CE | 同上 |
| 設定ファイルの読み込みと検証 | CE（CLI） | FEは設定ファイルを読まない |

FEの近隣表は「次の転送先 → MACアドレスと出力ポート」の表でしかない。表にない宛先へのパケットが
来たら、FEは解決依頼をCEへ送る（流量制限付き）。

## CEの組み立て方

### プロセスを分ける基準

次のどれかに当てはまるときだけ分ける。それ以外は分けない。

1. FEの表の書き手が違う。
2. 落ち方や再起動の都合が違う。
3. 別のプロジェクトとして開発している。

### 一つの表に書き手は一つ

```
 設定管理（ruster-confd） → インターフェース/アドレス表、NAT/firewallルール表
 経路の選択（ruster-ribd） → 経路表
 近隣の解決（ruster-neighd） → 近隣表
 DHCP / DNSなど    → 表には書かない。パケットの受け渡しだけ
```

- FEは「この接続はこの表に書いてよいか」だけを確かめ、書き手どうしの調停はしない。
- 経路の提供元（設定の静的経路、直結経路、DHCP、ルーティングデーモン）は経路を`ruster-ribd`へ渡し、
  `ruster-ribd`が選んだ結果だけをFEへ書く（[`overview.md`](overview.md)）。
- CEのプロセスどうしは、必要な相手と直接つなぐ（例: DHCP clientが受け取ったdefault経路を
  `ruster-ribd`へ渡す）。共通のバスは置かない。

### 管理の手段

中央の管理プロセスは置かない。次の三つで足りる。

| 必要なこと | 手段 |
|---|---|
| 起動、停止、再起動、依存順 | systemd |
| 相手の見つけ方 | 固定のsocketパス（例: `/run/ruster/fe/route.sock`） |
| 誰が何を書けるか | 表ごとにsocketを分け、ファイルの権限で制御する |
| 設定 | rusterの設定は`ruster-confd`が持ち、CLIから検証と反映を頼む。外のデーモンの設定はそのデーモン自身が持つ（[`ce-processes.md`](ce-processes.md)） |
| 状態の表示 | 各プロセスが自分の状態を返し、CLIが並べる |

全員で共有するのは、メッセージ形式とそれを読み書きするライブラリだけ。FEとCEの間も、CEどうしも
同じ形式を使う。

## FEとCEの間のやり取り

- 経路はUnix socket。
- 表の更新は「開始 → 追加/削除 → 確定」のまとまりで行う。確定した分だけが、FEの処理の
  切れ目で一度に反映される。
- 更新は差分で送れる。表全体を作り直す必要はない。
- 表をまたぐ参照（例: NATルールが指すインターフェース）は確定時に確かめ、相手がいなければ
  そのエントリを無効として扱う。書き手が後から整合を取り直す。
- 複数のプロセスにまたがって一度に反映する仕組みは作らない。必要にならない設計にする。

### CEが落ちたとき

- 接続が切れても、FEは表を最後の状態のまま保ち、転送を続ける。
- 再接続したCEは表全体を送り直す。FEは送られてこなかったエントリを消す。

## ルータ宛ての通信

ルータ自身が送り、受ける通信は、二つの原則だけで扱う。機能ごとの特別扱いは作らない。

- L2の制御のフレームは、種類ごとに決めた担当のプロセスへそのまま渡す。
- IPの通信では、kernelを「FEの内側にいるホストの一つ」として扱う。FEの機能は、ほかのホストの
  通信と同じようにルータ自身の通信にも効く。

### L2の制御のフレーム

ARP、ND、RA、DHCP、DHCPv6、PPPoEのDiscoveryとセッションの制御（LCP、認証、IPCP、IPv6CP）は、
FEから担当のCEプロセスへそのまま渡す。CEが作ったフレームはFEがそのまま送り出す。

- 渡し先は一つの表で決める。行は「インターフェース、種類（ethertype、IPのプロトコルとポート、PPPの
  プロトコル）、渡し先のsocket」。ARPとNDをneighdへ渡すのも、この表の一行にする。
- 表に無い種類は捨てて数える。
- PPPoEのセッションの制御は、セッションのインターフェースの親で受けたフレームを渡す。
  セッションが確立したあとの値（セッションの番号、相手のMAC）は、担当のデーモンがconfdかFEの表へ書く。

### IPの通信: kernelは内側のホスト

BGP、SSH、DNS、NTP、管理APIなどは、Linux kernelのTCP/IPスタックで終端する。

- VRFごとのTUNは、FEから見るとそのVRFの内側のインターフェースの一つで、その先にkernelという
  ホストが一台いる。
- **kernelから出るパケット:** TUNから読んだパケットは、LANのポートで受けたパケットと同じ転送の
  処理を通る。firewall、NAT、トンネルやPPPoEの包み、フラグメント、出口に入らないときのICMPエラー
  （kernelへ返る）がそのまま効く。firewallの規則では、kernelのインターフェースを`rt-<VRF名>`
  （default VRFなら`rt-default`）と名前で書く。たとえばMAP-Eでは、ルータ自身のDNSやNTPも共有のIPv4 addressと
  PSIDのポートに変換される。
- **kernelへ入るパケット:** トンネルを外し、NATを逆に変換した結果の宛先がルータのアドレスなら、
  FEはパケットをTUNのインターフェースへ転送する。ルータ自身が始めた通信の戻りは、NATの対応で
  kernelへ届く。ルータ宛ての通信は、kernelのインターフェースへ出ていく通信としてforwardのfirewallで決める（規則では`egress = "rt-default"`）。
- **送信元アドレス:** kernelは自分に設定されたアドレスを送信元に使う。出口で変換が要るかどうかは
  FEが決め、kernelはPSIDやトンネルを知らなくてよい。NATがあるときは、既定経路も直結の経路も
  NATの内側のアドレスを送信元にする。WANと同じサブネットの相手（ISPのゲートウェイなど）へも、
  LANのホストと同じくNATで変換されて出て、戻りがNATの対応で届く。
- **TTLとHop Limit:** ここだけはほかのホストと違う。TUNから読んだパケットと、TUNへ出すパケットは、
  ルータ自身が送り、受けたものなので、TTLとHop Limitを減らさない。TTL 1で送る直結のeBGPや、
  TTL 255で受けたことを確かめるGTSM（RFC 5082）がそのまま動く。
- **wan側で待ち受けるサービス:** NATの外側のアドレスで待ち受けるポート（SSH、管理APIなど）は、
  NATのポートの範囲から外して設定する。そのポートに届いたパケットは、NATの対応を探さずに
  input firewallへ進む。MAP-Eでは、待ち受けもPSIDのポートの組の中から選ぶ。UDPのサービスは、
  受けたアドレスから返す（`IP_PKTINFO`などを使う）。NATがあるときkernelが選ぶ送信元は内側のアドレスなので。
- TAPではなくTUNを使い、kernelにARP/NDをさせない。
- kernelは専用のnetnsに置き、フォワーディングは無効にする。kernelの経路は「全部TUNへ」だけ。
- アドレスはCEからkernelへ一方向に設定する。kernelからrusterへ情報を取り込まない。
- VRFごとにTUNを一つ持つ。FEはパケットのVRFでTUNを選び、TUNから読んだパケットはどのTUNから来たかで
  VRFが決まる。パケットにVRFの印は付けない。
- kernel側は、一つのnetnsの中にLinuxのVRFデバイス（l3mdev）をVRFごとに作り、そのVRFのTUNをぶら下げる。
  デーモンはsocketをVRFデバイスへ結び付ける（`SO_BINDTODEVICE`）。業界の主流でFRRの既定と同じ。
  - VRFごとにnetnsを分ける方式も、`ruster-confd`の選択肢として残す。VRFの間に強い分離が要るときに使う。
    どちらにしてもFEは変わらない。
  - 非常に多いVRF数（数千以上）での限界は確かめていない。そこまでの規模は今は目指さない。
- kernelとの出入口は差し替えられる形で作る。必要になった環境でだけ、速い方式
  （複数キューのTUN、virtio-user/vhost-net）やユーザー空間スタックに替える。

### ルータ宛て通信の保護

FEは、CEやkernelへ渡すパケットを種類ごとに分類し、それぞれに流量の上限と優先度を付ける。

- 最優先: BGP、BFD、ARP/ND
- 次: SSH、管理通信、DHCP
- 最後: ICMP、その他

溢れたら優先度の低いものからFEで捨て、分類ごとに捨てた数を数える。
kernelへの分類と上限は、パケットをTUNのインターフェースへ転送する直前、input firewallの後で掛ける。

### kernelに渡さない通信

大量になりうる通信はkernelに渡さない。トンネル（MAP-E、DS-Lite、GRE、VXLAN）の中身は
FEが転送として処理する。DPUのホスト宛て通信もFEの普通の転送になる。
