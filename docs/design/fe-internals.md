## 1. 役割とthread

CPUのコア数、NICのqueue数、コアを固定できるか（VMでは難しい）、DPUのARMコアの数は、置く場所によって
大きく違う。そのため設計では「役割と、役割ごとに守ること」だけを決める。何threadで動かし、どのコアに
置くかは起動時の引数で決める。

### 役割

| 役割 | 仕事 | 守ること |
|---|---|---|
| worker | パケットの受信、処理、送信。NATやfirewallの状態を持つ | 下の共通の決まりに加え、メモリを確保しない |
| 制御 | CEとのメッセージ、表の新しい版の作成、古い版の解放、状態の集計 | パケットに触らない |
| 受け渡し | ルータ宛て通信をCEのsocketとTUNへ書く、CEとkernelから読んでworkerへ渡す | 表を書かない |

全部の役割に共通の決まり: 待つsystem callとlockを使わず、一回の呼び出しでする仕事の量に上限を付ける。
制御の「表の新しい版を作る」のような重い仕事も、何回かの呼び出しに分けて進める。これがあるので、
どの役割も同じthreadに同居できる。

- workerの一回りは「受信をまとめて取る → 1パケットずつ最後まで処理 → まとめて送る」。途中で別の役割へ
  処理を渡す段階は作らない（後の「状態の持ち主」への受け渡しだけが例外）。
- どのworkerも、どのポートへでも送れる。そのやり方（workerごとの送信queueか、送信queueを持つworkerへ
  渡すか）はI/O層が決める。

### 仕事と実行役

役割の中身は「仕事」に分ける。workerは1つずつが一つの仕事、制御と受け渡しもそれぞれ一つの仕事。
仕事はどれも同じ形をしている。

```
仕事.進める(今の時刻) → { 何かしたか、次に呼んでほしい時刻、待つべきfd }
```

threadは「実行役」で、仕事の並びを受け取り、順に`進める`を呼び続けるだけ。役割のことは知らない。

```
実行役の一回り:
  並びの仕事を順に「進める」
  どれも何もしなかったら待つ
    回り続ける設定なら、すぐ次の回りへ
    poll設定なら、全仕事の「待つべきfd」と「次に呼んでほしい時刻」の最も早いものまで待つ
```

起動時の引数で「実行役の一覧と、それぞれが持つ仕事、固定するコア、待ち方」を渡す。どの環境も
この一つの書き方で表せる。

```
多コアのサーバ:        小さな箱（2コア）:        試験（sim）:
  実行役 core=2: [worker0]  実行役 core=0: [worker0]  実行役: [worker0, worker1, 制御, 受け渡し]
  実行役 core=3: [worker1]  実行役 core=1: [制御, 受け渡し]   （時刻はsimが与える）
  実行役 core=4: [worker2]
  実行役 固定なし: [制御, 受け渡し]
```

- 仕事どうしは、同じthreadにいても別のthreadにいても、同じ一方向のqueueでやり取りする。
  同居しているときだけ別の道を通る、ということをしない。
- I/O層の受信queueと送信queueは、threadではなく仕事（worker）に割り当てる。
- 実行役の並びの順番は決まっているので、同じ入力と時刻なら同じ結果になる。simはこれを使う。
- 引数を省いたときは、使えるコアの数とNICのqueueの数から既定の並びを作る。

### 待ち方の選び方

- 回り続ける（busy poll）: 遅れが最小。コアを一つ使い切る。
- `poll`で待つ: 電力とCPUを使わない。最初のパケットの遅れが少し増える。

実行役ごとに選べる。workerだけ回り続け、制御と受け渡しは`poll`で待つ、もできる。

## 2. 1パケットが通る処理の順番

### 受信してから転送するまで

```
受信
 ├ L2: 宛先MACの確認（自分、broadcast、受けるマルチキャスト）
 │     VLANタグ → サブインターフェース、PPPoEセッション → PPPoEインターフェース
 │     ARP、PPPoE Discovery、PPPの制御 → 受け渡し（5.）
 ├ L3の入口: IPv4/IPv6ヘッダの検証、ありえない送信元の破棄、uRPF
 │     受信インターフェースのVRFが、このパケットのVRFになる
 ├ ルータ宛てか（そのVRFのFIBでlocal）
 │   ├ トンネルの中身（IP in IP、WireGuardのデータ）→ 外して、トンネルのインターフェースで受信し直す
 │   └ それ以外 → firewall input → 受け渡し（5.）
 ├ 戻りの通信の変換: NATの対応に当たれば宛先を戻す（外 → 内）。ポート開放（dst-nat）もここ
 ├ TTL / Hop Limitを減らす。0ならICMP Time Exceeded
 ├ FIBを引く（VRFごと）。discardなら捨て、rejectならICMP Unreachable、lookup-vrfなら別のVRFで引き直す
 ├ firewall forward（状態を追う）
 ├ 送信元の変換: NAPT（MAP-Eならポート範囲の中で選ぶ）、NPTv6
 ├ 出口のMTU: IPv4でDF=0なら分割、そうでなければICMP Fragmentation Needed / Packet Too Big
 ├ 出口がトンネルなら包み、下側のVRFでFIBを引き直す（外側のMTUも確かめる）
 └ L2の出口: 近隣を引く（無ければ待たせて解決依頼）、VLANタグやPPPoEを付ける → 送信
```

- 順番はLinuxのnetfilterと同じ考え方にする（宛先の変換 → 経路 → firewall → 送信元の変換）。
  firewallは「宛先を戻した後、送信元を変える前」のアドレスを見る。慣れた順番なので説明しやすい。
- トンネルを外したり包んだりした後の「受信し直し」「引き直し」は同じworkerの中で行う。
  別のVRFでの引き直しも同じ扱い。段数に上限（トンネルと合わせて2段）を設け、超えたら捨てる。
- IPv6ではルータは分割しない。Packet Too Bigを返すだけ。

### ルータ自身が送るパケット（kernelからTUNで出てきたもの）

```
TUNから読む → firewall output → FIBを引く（TUNのVRF）→ 送信元の変換 → 出口のMTU → トンネル → L2の出口
```

送信元の変換を通すのは、MAP-Eのようにポート範囲が限られているとき、kernelが選んだポートを範囲内へ
直す必要があるため。

### CEが送るフレーム（ARP、DHCP、PPPoEの制御など）

CEは送り先のインターフェースを指定する。受け渡しと送り出しの形は対称にする。

- 受け渡すのは「そのインターフェースから見たフレーム」。VLANのサブインターフェースならタグを外した
  Ethernetフレーム、PPPoEのインターフェースならPPPのフレーム。
- CEが送るときも同じ形で渡し、FEがインターフェースの種類に応じてタグやPPPoEを付ける。

### FEが作るパケット

ICMPエラー、分割したフラグメント。workerが送信先ポートのbufferに直接作る。

- ICMPエラーの速さはFE全体の上限をworkerの数で割って、workerごとに守る。
- NATで変換したパケットへのICMPエラーは、変換前の形に戻してから作る。

## 3. 状態の持ち主

NATのセッション、firewallで追っている通信、フラグメントの組み立て、解決待ちのパケットは、
どれか一つのworkerだけが持つ。他のworkerは読まない。

問題は、行きと戻りのパケットが別のworkerに届くこと。NICの振り分け（RSS）は受信したパケットの
アドレスとポートで決まり、NATでアドレスやポートが変わると行きと戻りで結果が変わる。

### 決め方

「その通信の持ち主のworker」を、パケットの中身から計算で決める。持ち主でないworkerが受け取ったら、
持ち主へ渡す。

| 通信 | 持ち主の決め方 |
|---|---|
| NATの外から戻ってくる通信 | 宛先ポート（変換後のポート）で決める。各workerは変換後のポートの範囲を分けて持つ |
| NATの内から出ていく通信 | 内側のアドレスとポートの組から計算する。持ち主は自分の持つポートの範囲から変換後のポートを選ぶ |
| NATしない、状態を追う通信 | 両方向で同じ値になる計算（送信元と宛先を並べ替えてから計算）で決める |
| 状態を持たない通信 | 受け取ったworkerがそのまま処理する |

- workerの間はworkerの組ごとの一方向のqueueでつなぐ。lockは使わない。
- MAP-Eでポート範囲が限られていても、その範囲をworkerの数で分ける。
- workerが一つなら受け渡しは起きない。

### 受け渡しを減らす工夫（任意）

戻りの通信はworkerの数が増えるほど他のworkerへ渡す割合が増える。NICが宛先ポートの値で受信queueを選べる
（ethtoolのntupleなど）なら、「ポートの範囲 → 持ち主のworkerのqueue」をNICに設定し、受け渡しを無くせる。
これはI/O層の任意の機能で、無くても正しく動く。

## 4. 表の更新の届け方

### 読むだけの表（FIB、近隣、インターフェース、NATとfirewallの設定、受け渡しの分類）

```
制御:   新しい版を作る → 「今の版」を新しい版に差し替える（一つのポインタの書き換え）
worker:     一回りの最初に「今の版」を読み、その回りの間はその版だけを使う
            回りの終わりに「ここまでの版は使い終わった」と印を付ける
制御:   全workerが新しい版に移ったら、古い版を解放し、CEへ応答を返す
```

- workerはlockを取らず、待たない。読むのはポインタ一つと、自分の印の書き込みだけ。
- 一回のiPATCHが一つの版になる。版は送られた順に入れ替わる。短い間に届いた複数のiPATCHは、
  一つの版にまとめてよい（応答はそれぞれに返す）。
- CEへの応答は、全workerが新しい版に移ってから返す。応答を受け取った時点で、全workerが新しい表を使っている。

### 大きい表（FIB）

BGPのフルルートは100万経路あり、更新も多い。更新のたびに表全体を作り直すと間に合わない。

- 経路の表は、更新した部分の道筋だけを新しく作り、残りは前の版と共有する木にする。
  1経路の更新で作り直すのは木の深さ分だけ。
- 検索の速さと更新のしやすさの釣り合いで、具体的な形（1段で何bitずつ進むか）は実装時に測って決める。

### workerが持つ状態と表の関係

表の変更でworkerの状態が古くなることがある（NATのルールが消えた、インターフェースが消えた）。

- 版には番号を付ける。workerは版が変わったことに気づいたら、古くなりうる状態を少しずつ確かめて消す。
  一回りで確かめる数には上限を付け、転送を止めない。
- 次にパケットが当たったときにも確かめる。

### workerの状態を読む

- カウンタはworkerごとに持ち、workerだけが書く。制御の役割は足し合わせて読む。
- NATのセッションの一覧のように大きいものは、制御の役割がworkerへ「次のN件を写して」と頼み、
  workerが一回りの空き時間に少しずつ写す。

## 5. ルータ宛て通信の受け渡し

```
worker: 分類 → 種類ごとの上限 → 受け渡しの役割へのqueueにコピー
受け渡し: 種類ごとのsocket、またはVRFのTUNへ書く（待たない）
```

- 種類ごとの上限は、FE全体の上限をworkerの数で割ってworkerごとに守る。
- コピーするのは、ルータ宛ての通信は転送の主な流れではなく、bufferをNICへ早く返すため。
- socketやTUNが詰まっていたら捨てて数える。workerは待たない。

逆向き:

- CEからのフレーム: 受け渡しの役割が読み、どれか一つのworkerへのqueueに入れる。workerが送信する。
- kernelからのパケット（TUN）: 状態の持ち主の決め方（3.）で選んだworkerへのqueueに入れる。
  送信元の変換（NAT）を通るため。

## 6. メモリ、時刻、溢れたとき

### メモリ

- 起動時の引数で容量を受け取り、全部を起動時に確保する。workerは動作中にメモリを確保しない。
- workerの状態（NATのセッションなど）は、workerごとに分けた入れ物に入れる。
- 表の版は、新旧二つが同時に存在できる分を見込んで確保する。

### 時刻

- workerは一回りに一度だけ時刻を読み、その回りの間はその値を使う。
- 期限のある状態（セッション、フラグメント、解決待ち）は、期限ごとに並べた入れ物で管理し、
  一回りで処理する数に上限を付ける。

### 溢れたとき

- queue、表、状態の入れ物は全部大きさに上限がある。溢れたら捨てて、理由ごとに数える。
- 捨てた理由はすべて名前の付いた種類にし、`show`で見られる。

## 7. I/O層に求めること

I/O層（AF_XDP、AF_PACKET、sim、将来は他）は、NICやドライバの違いを吸収する。

### 必須

- 受信したパケットのbufferを、まとめて貸す。workerは書き換えてそのまま送るか、返す。
- FEがパケットを作るためのbufferを、送信先のポートから借りる。
- 借りたbufferは、送信、返却のどちらかで必ず一度だけ終わる。
- workerごとに独立した受信queueと送信queueを持てる。

### 任意（あれば使う、無くても正しく動く）

- bufferをworkerの間で移せる（無ければ、持ち主への受け渡しのときにコピーする）。
- 宛先ポートの値で受信queueを選べる（3.の受け渡しを減らす）。
- checksumの計算をNICに任せられる。

## 起動時の引数

表ではなく、FEの起動時に決めるもの。変えるにはFEの再起動が要る。

- ポート: 名前と、使うNIC、queueの数、I/O層の種類
- 実行役の一覧: それぞれが持つ仕事（workerの数はここで決まる）、固定するCPUコア（固定しなくてもよい）、待ち方
- 各表と状態の容量
- CEとつなぐsocketを置くdirectory

## 今のコードとの違い

設計図だけの段階なので直さないが、実装へ進むときに影響する。

- 今はworkerが一つで、NATやfirewallの状態の持ち主を決める仕組みが無い。
- 今は設定全体から新しい版を作って差し替える。差分の更新と、一部を共有する経路の表が無い。
- 今はARPの解決をFEの中で行っている（設計ではneighdへ出す）。
- 今のI/O層の決まり（bufferを借りて必ず一度だけ終える）は、そのまま使える。
