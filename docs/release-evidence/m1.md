## criterionごとの証跡

以下のcommandはすべてrepository rootで実行し、2026-10-31に`477f2ef`上で記載どおり成功する
ことを確認した。`target/debug/ruster`は`cargo build --locked -p ruster-cli`で作る。

### 1. validate / plan / run-sim（met）

`ruster-cli`（binary `ruster`、#279）。手書きarg parsing、value-free diagnostic、exit status
`0`/`1`/`2`。tests: `usage_errors_are_typed`（CLI-001）、
`validate_reports_summary_or_typed_diagnostics_with_exit_status`（CLI-002）、
`plan_output_is_deterministic_and_reports_restart_reasons`（CLI-003）、
`run_sim_matches_the_golden_output_byte_for_byte_twice`（CLI-004）、
`run_sim_failures_map_to_exit_statuses`（CLI-005）。

```bash
cargo build --locked -p ruster-cli
target/debug/ruster validate fixtures/m1/router-v1.toml           # exit 0、valid: schema-version=1 ...
target/debug/ruster validate fixtures/m1/router-invalid.toml      # exit 2、stage=validate code=GATEWAY_NOT_ON_LINK
target/debug/ruster validate fixtures/m1/router-missing-nat.toml  # exit 2、stage=bridge code=MISSING_SERVICE_NAT44_UDP
target/debug/ruster plan fixtures/m1/router-v1.toml fixtures/m1/router-v2.toml        # plan: reloadable
target/debug/ruster plan fixtures/m1/router-v1.toml fixtures/m1/router-capacity.toml  # plan: restart-required、STORAGE_SHAPE
cargo test --locked -p ruster-cli --test cli
```

### 2. M1 golden scenario through public full composition（met-with-deviation）

`fixtures/m1/scenario.toml`を`SimIo`上の`run_tick`＋`ActivePublication`で実行する（#278）。
test `m1_golden_scenario_passes_and_matches_golden_output`（SIM-010）が全`expect`の成功と
`fixtures/m1/expected.jsonl`とのbyte一致を確認する。golden出力は66行（start 1、inject 17、
tick 19、tx 13、apply 5、expect 10、final 1）。

coverage: LAN/WAN static route、ARP Request生成→Reply学習→学習MACで転送（dynamic ARP）、
UDP/TCP SNATとreply de-NAT、FW rule allowとdeny、NAT mapping miss、TTL 1→Time Exceeded
Type 11/Code 0、応答しないconnected hostへARP 3回→Destination Unreachable Type 3/Code 1。

**deviation（a）**: full compositionはfirewall必須で、coreはfirewall有効時のroute missを
silentな`FIREWALL_ROUTE_UNAVAILABLE`でdropする。したがってDestination Unreachable Network
（Type 3/Code 0）は生成されず、scenarioはsilent dropだけを検証する（RFC 1812 §5.2.7.1からの
deviation）。M1はfirewallを必須とするため、exit criterionの「route ICMP」は満たしていない。
development plan「M1 owner決定」の補足でowner確認待ちとして記録済みで、ledger SIM-010は
`deviation`。修正案はegress=noneでingress ruleとdefault policyを評価するcore変更
（`crates/core/src/forwarding.rs`の`decide_ipv4`、io-sim `stateful_firewall.rs`のtest、
architecture記述、golden再生成）。

```bash
cargo test --locked -p ruster-sim-scenario --test driver
```

`run_sim_output_never_contains_the_seed`（SIM-014）、CLI-004（process経由で2回）。

### 5. reload / restart-required / rollback（met）

- reloadは`run_tick`先頭のpublication phaseだけで行う（RT-001〜003、PUB-006）。
- restart-required: storage shape、Resolution/ICMPv4 policy、interface IfId/MAC変更を
  `RestartRequired`でreject（PUB-003 `successor_checks_generation_keys_shape_and_fixed_policies_without_apply`、
  PUB-008 `plan_restart_classification_matches_live_apply_rejection`）。
- rollback: 旧config文書を再validateし、新generation・新keyでapply
  （PUB-009 `rollback_reapplies_old_document_as_new_generation_with_new_keys`）。
- golden: step 28でv2をgeneration 2としてapplyしflush数を出力、step 38 `STORAGE_SHAPE`、
  step 39 `INTERFACES`をrestart-requiredでreject（candidate generation 3、4は消費）、step 43で
  v1をgeneration 5として再apply。

補足（owner確認待ち、M1 closeを妨げない）: NAT port poolの**size**変更はstorage shapeを変えるため
restart-required、同sizeのrange shiftとrealm変更はreload可能（#275、PUB-008）。run-simは
restart-requiredをrejectとして報告し、同一process内でstorageを作り直さない（SIM-016 deferred）。

```bash
cargo test --locked -p ruster-control --test publication successor_checks_generation_keys_shape_and_fixed_policies_without_apply
cargo test --locked -p ruster-control --lib -- plan_restart_classification_matches_live_apply_rejection rollback_reapplies_old_document_as_new_generation_with_new_keys
```

### 6. SIGINT/SIGTERM ordered shutdown（met）

`--hold`はscenario後もidle tickを続ける。signal handlerはstatic `AtomicBool`へstoreするだけで、
CLIはtick境界で停止→backend quiescence（未完了batch、live lease、未完了TXなし）を確認→
`final` eventを書いてexit 0。tests: `hold_mode_shuts_down_in_order_on_sigterm`（CLI-006）、
`hold_mode_shuts_down_in_order_on_sigint`（CLI-007）。

```bash
cargo build --locked -p ruster-cli
target/debug/ruster run-sim --scenario fixtures/m1/scenario.toml --hold > /tmp/m1-hold.jsonl 2> /tmp/m1-hold.err &
pid=$!; sleep 1; kill -TERM "$pid"; wait "$pid"; echo "exit=$?"
tail -n 1 /tmp/m1-hold.jsonl | cut -c1-60
cat /tmp/m1-hold.err
```

期待: `exit=0`、最終行が`{"event":"final",...,"generation":5,...`、stderrが
`holding at generation 5`と`stopped by signal ... generation 5`。`at_ms`とtick数はsleep時間に
依存する。job controlのないshellで`&`起動するとSIGINTはignoreを継承するため、手動確認には
SIGTERMを使う（SIGINTはCLI-007がprocess spawnで確認する）。

`generation_and_apply_outcome_are_reflected_once`ほか）。

## M1を閉じる手順

1. **(a) route-miss ICMP**: ownerがSIM-010 deviationを受容するか、core修正を選ぶ。
   - 受容: development plan「M1 owner決定」の該当補足を「決定」へ更新し、SIM-010は
     `deviation`のまま、architecture/requirementsのdeviation記述を維持する。
   - 修正: firewall有効時もegress=noneでingress ruleとdefault policyを評価するcore PR
     （`forwarding.rs`の`decide_ipv4`、io-simのfirewall test、architecture記述）を独立reviewで
     merge後、`RUSTER_UPDATE_GOLDEN=1 cargo test -p ruster-sim-scenario --test driver`で
     goldenを再生成し、Type 3/Code 0の`expect`を追加してSIM-010を`implemented`にする。
2. **(b) required checks**: repository adminがruleset `main-protection`のrequired status
   checksへ`R16A Bounded`と`Musl`を追加する（(c)後に`Benchmark Smoke`も追加）。上の
   `gh api .../rules/branches/main`で確認し、このfileの表を更新する。
3. **(c) R17**: ownerが#282のthresholdを承認または修正する。承認PRでstatusをAPPROVEDにし
   digestを再生成、draft-marker testを置き換え、BENCH-009を更新してmergeする。そのsquash
   merge commitを`spec_git_sha`、`docs/benchmark-spec-v0.2.sha256`の値を`spec_sha256`として
   このfileの「対象SHAとCI」へ記録する。R12 acceptanceどおり`ruster run-sim`へspec SHAを
   表示するならその小PRも同時期に行う。
4. 他の確認待ち事項（NAT port pool size、OBS-017/018）のowner回答をdevelopment planへ記録する。
5. 以上がmergeされた`main` SHAで`CI`、`Security Smoke`、`Benchmark Smoke`がsuccessで、それらが
   required checkであることを確認し、そのSHAとrun URLをこのfileへ追記して判定一覧の8、9
   （および2）を`met`へ更新する。この更新PRのmergeをもってM1 closeとする。
